Idea 3 of 3

Orchestration

One planner, several helpers. For a big job, the assistant you talk to splits the work and hands each piece to a helper.

The problem

One long conversation does too much

Picture a single chat that plans a job, reads the files, builds the result and checks it. It works for a while. Then it starts to struggle.

It fills up

Everything the assistant reads and writes stays in its context window: the working memory of one conversation. It has a fixed size, and a long job fills it.

It slows down and costs more

Each new message makes the assistant take in the whole conversation again. The longer it gets, the slower and dearer every reply is.

It loses the thread

Early decisions get buried under pages of detail. Late in the job, the assistant may forget what you agreed at the start.

The idea

Keep one conversation short, and share out the work

You talk to one assistant that only plans and coordinates. The heavy work happens elsewhere.

In plain terms

An orchestrator is the one conversation you talk to. It holds the plan and hands each piece of work to a subagent: a separate helper with its own fresh memory. The subagent does the work and sends back a short report.

The orchestrator never has to read every file or try every idea itself. It reads the reports and decides what happens next, like a project lead who works from team updates and not from everyone's notes.

A typical run

From your request to one summary

Take a software project as the example. The same pattern fits any job big enough to split into pieces.

  1. You describe what you want

    Say it in plain words, as you would to a colleague.

  2. The orchestrator asks questions until it is clear

    It would sooner ask now than build the wrong thing.

  3. It shows a short plan and waits for your yes

    You see what will be built, and by which helper, before any work starts.

  4. Helpers build the pieces

    Pieces that do not overlap are built at the same time. Each helper gets a short brief and works alone.

  5. A separate helper checks the result

    It looks at the work with fresh eyes. Another one checks that nothing private is about to be shared.

  6. One summary comes back to you

    What was built, what went wrong, and what is worth a second look.

A worked example

One question, five helpers

Here is the same pattern on an everyday data question. Each step says who does the work, on which model, and what comes back.

The request

"How has claims trend changed month over month, and is there a notable difference in the number of high-cost claimants?"

  1. The orchestrator asks, then plans

    Largest model

    It asks the two questions that change the answer. Which date counts: the date a claim was paid, or the date of service? And what counts as "high-cost", for example a claimant whose claims total over a set dollar amount in a year? Then it agrees a three-line plan with you: look at the data once, work out the trend and the high-cost counts side by side, check the figures and write the answer.

    Comes back: your two answers and a plan you have approved.

  2. The reader looks at the data once

    Small model

    It opens the data and reports what is in it, so nobody else has to open the whole file.

    Comes back: a few lines with the columns, the date range and the number of rows.

  3. Builder A works out the trend

    Mid-sized model at the same time as B

    It works out how claims changed from month to month and adds a trend chart from the design library.

    Comes back: the monthly figures, the chart and a short note on what it did.

  4. Builder B counts the high-cost claimants

    Mid-sized model at the same time as A

    It counts high-cost claimants in each period, using the definition you agreed, and adds a comparison chart or table from the library.

    Comes back: the counts, the chart or table and a short note on what it did.

  5. The checker re-runs both

    Mid-sized model

    It repeats both calculations from the data and confirms that every figure in the text matches. This is the reviewer role from the picture above.

    Comes back: a pass, or a list of figures that do not match.

  6. The orchestrator writes the answer

    Largest model

    It reads the four short reports and writes the answer in plain words, with the two charts. Nothing here is shared outside, so the safety check is not needed. It would run before anything is shared.

    Comes back to you: one answer with its charts.

One conversation

Largest model only

About 40 steps. The conversation grows from about 15,000 to about 150,000 tokens, so each step re-reads about 80,000 on average.

  • Re-reading: 40 × 80,000 = 3.2M tokens × $0.20 = $0.64
  • New material read (data peeks, results, errors): 135,000 × $5.00 = $0.68
  • Written (code, reasoning, the report): 45,000 × $20 = $0.90
  • Total: about $2.20

So the orchestrated run costs roughly $1.00 against roughly $2.20. The two builders also run at the same time, so it finishes sooner. The saving comes from three places.

Less is re-read

Each helper's conversation stays short, so far less is re-read at every step: 3.2M tokens in one conversation against about 1.2M across all the helpers.

Building costs half as much

The building is done on a model that costs half as much per token.

The first look is nearly free

The one-off look at the data is done on a model that costs a fortieth as much.

The honest limits

  • These are estimates built from assumed step counts. A harder question, more retries or a larger data sample changes both sides.
  • Orchestration has a fixed overhead. Each helper must be briefed and starts from nothing. For a question one chart can answer, a single conversation is cheaper.
  • The smaller model should not be the one deciding what "high-cost" means. That is why the orchestrator settles definitions before any building starts.

Roles

Different helpers, different models

A model is the AI engine behind an assistant. Some are small and quick, some are large and thorough. Each helper gets the one that suits its job.

Small, fast model

The reader

Answers one pointed question, such as "where is this set up?". It needs speed, not deep thought.

Most capable model

The builder

Does the real construction. Mistakes here cost the most, so this is where the strongest model goes.

Fresh eyes

The reviewer

Looks at the result without having seen how it was made. That distance helps it spot what the builder missed.

Before sharing

The safety check

Looks only for things that should not leave, such as keys, personal details and private paths.

Mid-sized model

The routine helper

Handles mechanical steps that follow clear rules, such as saving work and tidying files.

Why match the model to the job

Larger models cost more and take longer per answer, so using one for every small task wastes both. Giving the strongest model only the hard work keeps quality where it matters, and keeps the bill and the wait down everywhere else.

Efficiency

Why this is efficient, and what it costs

Orchestration saves time and keeps the conversation clear. It does not remove work. It moves it to shorter conversations and cheaper models.

The conversation stays short

A helper's reading and trial and error stay in its own memory. Only its short report comes back, so the conversation you are in stays focused.

Independent pieces run together

Work that does not overlap is done at the same time, so the whole job finishes sooner.

Cheap models do cheap jobs

Small jobs go to small models. The strongest model is kept for the work that needs it.

In plain terms

Token: a small piece of text, roughly a word or part of one. Assistants read and write in tokens, and usage is counted in them.

The trade-off

Orchestration does not remove work. It moves it to shorter conversations and cheaper models. In one real build, the helpers together worked through several million tokens, while the planning conversation received only their short reports. That is a lot of effort, so orchestration is for sizeable jobs. Small fixes are done directly.

Safety

What keeps it safe and predictable

Four habits keep you in charge and stop it running away.

Your yes comes first

Nothing is built before you approve the plan.

Each helper has a boundary

Every helper is told exactly which files it may touch, so two helpers do not overwrite each other.

Work happens on a branch

A branch is a separate copy of the project's history. The work stays there, apart from the main version, until you accept it.

A fixed limit on fix rounds

If a check fails, the helper may try again, but only a set number of times. After that it stops and tells you, so it cannot loop for ever.

Not tied to one tool

The pattern is written so it does not depend on one vendor's assistant. The same planner-and-helpers way of working applies in Claude Code and in Cursor.
