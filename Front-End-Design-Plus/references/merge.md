# Merging saved visuals into the deliverable

## What the whiteboard leaves in `<out>/`

| File | Contents |
|---|---|
| `result.json` | `{library, done, saved: [{id, title, library, kind, file}], board}`: the saved IDs in order, each with the path of its recipe file. `done` is false if the page was closed without Done. |
| `<id>.json` | One saved recipe: `{id, parent, title, library, kind, code}`. No data. |
| `board.json` | Every card, for resuming. Not needed for merging. |

- `kind` is `chart` or `table`. A table always has `library: "html"`, whatever the session library.
- `code` is the body of `render(el, rows, lib)`: `el` is an empty, sized box; `rows` is the array of row objects from the data file; `lib` is the library global.
- Tell the user which IDs were saved (ID and title), then ask or follow their direction: add, or replace the existing visual.

## The merge, in every library

1. Wrap the code once per recipe: `function renderG3(el, rows, lib) { <code> }`. Keep the code as it is.
2. Give it a container with an explicit height (for example `height: 360px`); charts draw nothing in a zero-height box.
3. Call it with the deliverable's own rows (the same rows written to the data file) and the library global.
4. When replacing a visual, remove the old chart code and its container, or reuse the container.
5. Resizing: most recipes end with their own `ResizeObserver` on `el` (Plotly and Chart.js resize through their `responsive` option instead). Keep it, so the visual follows its container. Drop that one line only if the deliverable already resizes its charts itself (for example a shared resize handler), so it is not done twice.
6. If the deliverable's rows differ from the data file (other column names, pre-aggregated), adapt only the column names inside the recipe; tell the user.

| Library | Call | Notes |
|---|---|---|
| `echarts` | `renderG3(div, rows, echarts)` | Before redrawing into the same div, `echarts.getInstanceByDom(div)?.dispose()`. |
| `plotly` | `renderG3(div, rows, Plotly)` | Returns a promise; `Plotly.purge(div)` before redrawing. |
| `chartjs` | `renderG3(div, rows, Chart)` | Appends its own canvas. The recipe may set `Chart.defaults` fonts and colours; that is global. Destroy the old chart (`Chart.getChart(canvas)?.destroy()`) before redrawing. |
| `vegalite` | `renderG3(div, rows, vegaEmbed)` | Needs `vega`, `vega-lite` and `vega-embed` loaded. Returns a promise. |
| `d3` | `renderG3(div, rows, d3)` | Clear the div (`div.innerHTML = ''`) before redrawing. |
| `html` | `renderG3(div, rows)` | No library. Styles are inside the markup with `fdp-` class names, so they do not leak. |

## By kind of deliverable

- **Static HTML page:** the library is already loaded by the page. Add a `<div id="g3" style="height:360px"></div>` and a `<script>` with the wrapped function and the call, after the page's data is available.
- **React (or another component framework):** a component with a `ref` on a sized `div`; call the function in `useEffect` with the rows and the library import, and clean up on unmount (dispose, purge or destroy as above).
- **Page generated by a Python script:** the script already embeds the data as JSON for the browser. Put the wrapped function in the template and call it with that JSON.
- **Several saved IDs:** one container and one wrapped function each, named by ID.

## Checks after merging

- Open the deliverable (or run its build) and confirm each merged visual draws.
- Search the merged code for typed-in data values; there should be none (recipes aggregate from `rows`).
- Leave the temp session folder in place until the user is happy; it holds the board for resuming.
